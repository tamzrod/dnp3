## 2. G41V2 wire contract (implemented)

Verified independent OpenDNP3 3.1.2 Group 41 object (AO-001 §3.1): a signed **int16** value
serialized **little-endian** followed by **one command-status octet**. G41V2 is `0x29 0x02`.

Direct Operate request object (qualifier `0x28` = 16-bit count + 16-bit index), index 0:

```
29 02 28 01 00 | <index LE 2> | <int16 value LE 2> | 00 (request status = SUCCESS)
```

Outstation response: the same object echoed under `0x28` with the status octet replaced by the
command result. Master acceptance requires the echoed group/variation/index **and** value to match
the request exactly; a missing, truncated, mismatched or wrong-variation object is never success.

Independent golden vectors (AO-001 §6.1), frozen as literal bytes in the tests:

| Case | Value bytes (LE) | Full record @ index 0 |
|---|---|---|
| G41V2 int16 = 42 | `2A 00` | `29 02 28 01 00 00 00 2A 00 00` |
| G41V2 int16 = −32768 | `00 80` | `29 02 28 01 00 00 00 00 80 00` |

## 3. Implementation summary

- **Master** (`internal/master/master.go`): the G41 request builder now encodes V1 (int32) and V2
  (int16); a single `g41ValueWidth(variation)` derives the value width (0 = unsupported). The
  request key, response parser (`parseG41Record`), echo-status resolver (`g41CommandStatus`) and the
  control-object size/layout helpers (`isControlObject`, `controlPointValueSize`, `objectLayout`) are
  generalized to the supported variations rather than hard-coded to V1. Added `controlInt16Value`
  (exact, range-checked; out-of-range is rejected, never wrapped) alongside `controlInt32Value`.
- **Outstation** (`internal/outstation/outstation.go`): `handleDirectOperate` validates the G41
  variation, count (exactly 1) and record length before any side effect; `executeControl` decodes
  V1/V2 little-endian and dispatches a typed `int32`/`int16`; `buildG41EchoObject` echoes the object
  with the correct width; the `handleWrite` G41 branch is generalized the same way.
- **Public API** (`pkg/dnp3/types/commands.go`, `pkg/dnp3/master/client.go`,
  `pkg/dnp3/outstation/server.go`): additive, backwards-compatible `AnalogInt16CommandValue` and
  `NewAnalogInt16Control`; the master object gate admits G41V2 (V3/V4 and non-control groups stay
  rejected before any wire traffic); the bridge maps a G41V2 write to a typed
  `*types.AnalogInt16CommandValue` with `DirectOperate` semantics and rejects a non-int16 or
  out-of-range int32 without narrowing.

No SBO, Direct-Operate-No-Response, G42–G44, batching, new qualifiers, or utility-specific point
mapping/units/policy were added. No silent float-to-int rounding, narrowing/wrap, or false SUCCESS.

## 6. Unresolved risks and blockers

- **G41V3/V4 (IEEE-754 float32/float64) are NOT implemented.** AO-001 §5.3 requires an **explicit
  policy** for `NaN`/`±Inf` (recommend reject at the API boundary) and §7.4 states that public-API
  and control-safety policy changes require the normal approval path, which AO-001 explicitly does
  **not** grant. The AO-003 task text likewise forbids "NaN/Inf acceptance without explicit policy".
  Implementing V3/V4 without an owner-approved float/NaN/Inf policy would be an unapproved
  design/safety decision, so it is recorded here as a **blocker/PUSHBACK**, not guessed.
- **No independent peer evidence.** The in-repo loopback gate is self-consistent (AO-001 D2) and is
  not interoperability evidence. AO-004 (isolated OpenDNP3 peer + original PCAP/.vec) is out of scope.
- **G41 remains UNSUPPORTED** in the profile; no compliance/production/NGCP claim is made.
