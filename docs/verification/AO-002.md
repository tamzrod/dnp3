## 2. G41V1 wire contract (implemented)

Verified independent OpenDNP3 3.1.2 Group 41 object (AO-001 §3): a signed **int32** value
serialized **little-endian** followed by **one command-status octet**. G41V1 is `0x29 0x01`.

Direct Operate request object (qualifier `0x28` = 16-bit count + 16-bit index):

```
29 01 28 01 00   group 41, variation 1, qualifier 0x28, count 0x0001
<index LE>       first point index (2 octets, low byte first)
<value LE>       signed int32, low byte first
00               request object command status (SUCCESS)
```

Independent frozen literals (AO-001 §6 / AO-002 acceptance #1), object header + record only
(no APDU function/IIN bytes):

| index | value | object bytes |
|-------|-------|--------------|
| 0 | `2300` | `29 01 28 01 00 00 00 FC 08 00 00 00` |
| 0 | `-1` | `29 01 28 01 00 00 00 FF FF FF FF 00` |

Both the master encoder and the outstation decoder are verified against these literals
independently — not against each other's output.

## 3. Implementation summary

- **Master encoder** (`internal/master/master.go`, `buildControlRequest`): the G41 branch now emits
  group `0x29`, variation `0x01`, qualifier `0x28`, count `01 00`, index low byte first, signed
  int32 low byte first, trailing `00`. Any other G41 variation, a non-`int32`/`int`/`int64` value,
  a float (even integral), or an out-of-range integer returns a `nil` request — a **definite
  pre-send rejection**, never a truncation, rounding or wrap. The prior non-conformant 16-bit
  path for G41 was removed; G42–G44 are no longer encoded (the `default` case rejects).
- **Master status parser** (`internal/master/master.go`): `parseCommandStatus`,
  `commandStatusForQualifier`, `skipObject`, `objectLayout` and `containsG12V1Header` are now
  group-aware via `isControlObject`/`controlPointValueSize` (G12V1 = 11-octet point; G41V1 =
  5-octet point: int32 + status). `resolveOperateStatus` takes the request APDU; for a G41V1
  request it requires the echoed object to match group/variation/**index** exactly
  (`g41v1CommandStatus`/`parseG41V1Record`) and never falls back to IIN success. G12V1 behavior is
  unchanged (including the IIN-only success path for G12V1).
- **Outstation parser** (`internal/outstation/outstation.go`): `executeControl` G41 branch and the
  `handleWrite` G41 branch accept **only** variation 1 with an exact 5-octet record
  (int32 LE + status); any other variation or wrong length is rejected with `ErrInvalidRequest`
  **without calling the host handler**. `handleDirectOperate` echoes the G41V1 object (index,
  int32 value, SUCCESS status) on success; a handler error yields an error response (never a
  SUCCESS echo).
- **Public bridge** (`pkg/dnp3/outstation/server.go`): a G41V1 write is carried as a typed
  `*types.AnalogInt32CommandValue` with `CommandType: DirectOperate` (previously hard-coded
  `SelectThenOperate`, now corrected). A non-`int32`/`int16` value is rejected before the handler.
- **Public gate** (`pkg/dnp3/master/client.go`): a fail-closed object gate admits only G12V1 and
  G41V1; any other group/variation is rejected with `ErrUnsupportedOption` **before any wire
  traffic**. G12V1 admission and the DirectOperate/SelectThenOperate/NoResponse command-type gate
  are preserved.
- **Types** (`pkg/dnp3/types/commands.go`): added `AnalogInt32CommandValue` (int32) and
  `NewAnalogInt32Control`; the legacy `AnalogCommandValue`/`NewAnalogControl` (float64 carrier) is
  retained for API continuity and is not the verified G41V1 path.

## 8. Owner-authorized corrective CWAL — F1/F2 fail-closed fixes (2026-11-11)

Authority: owner addendum `workflow/active_work/AO-002.md` "Owner-authorized corrective AO-002
CWAL — F1/F2", committed on `work` as `5ad4391` (baseline `b42e694`). This is the CURRENT AO-002
corrective scope, not a new task. Two independently identified control-status defects were fixed.

### F1 — fail closed when the DataHandler is not a DataWriter (`internal/outstation/outstation.go`)

`handleDirectOperate` previously logged `"data handler does not implement DataWriter!"` and
continued to construct a success response. For G41V1 the master reads the echoed object's
command-status octet, so that produced a **false success** with no execution. The branch now stops
with a classified error (`ErrNotSupported`, added to the outstation error set), sets
`ParameterError`, calls **no** handler and mutates **no** output state — it never builds a SUCCESS
echo. The G41V1 request-echo path below is only reached once a `DataWriter` exists.

- Shared fix: the fail-closed exit applies to any control object (not only G41V1), because a
  missing `DataWriter` means no control can execute; the previous G12V1 behavior in this branch was
  the same latent false-success. Verified G12V1 success semantics (with a `DataWriter`) are
  unchanged and covered by the existing CROB suite and the positive control below.

### F2 — nil analog status is not success (`pkg/dnp3/outstation/server.go`)

`internalDataHandler.WriteAnalogOutput` previously treated `status == nil && err == nil` as success
(it only failed when `status != nil && *status != ControlSuccess`). It now requires an **explicit**
`status != nil && *status == types.ControlSuccess && err == nil`; a nil status, an error, or any
non-SUCCESS status fails closed. No SUCCESS status is synthesized and a rejected command is never
coerced into success.

### Tests added

- `internal/outstation/g41v1_f1_failclosed_test.go`:
  - `TestOutstationG41V1NoDataWriterFailsClosed` — G41V1 DirectOperate with a non-`DataWriter`
    handler returns `ErrNotSupported`, no response object, no SUCCESS echo.
  - `TestOutstationG12V1NoDataWriterFailsClosed` — the shared fail-closed behavior for G12V1.
  - `TestOutstationG41V1DataWriterPositiveControl` — a valid `DataWriter` still executes G41V1 and
    returns the byte-exact SUCCESS echo (`00 00 29 01 28 01 00 00 00 FC 08 00 00 00`).
- `pkg/dnp3/outstation/analog_status_failclosed_test.go`:
  - `TestBridgeAnalogOutputF2FailClosed` — matrix: explicit `ControlSuccess` succeeds; `(nil,nil)`,
    `ControlNotSupported`, `ControlBlocked`, `ControlLocal`, and `(nil, error)` all fail closed.
  - `TestBridgeAnalogOutputF2FalseSuccessNotPropagated` — bounded in-repo end-to-end: the public

### F3 — validate G41V1 Direct Operate count before side effects (`internal/outstation/outstation.go`)

`parseControlObjectHeader` returns a count, but `handleDirectOperate` discarded it, so a batch or
empty G41V1 request could reach `WriteAnalogOutput`. This first slice supports exactly **one** G41V1
point per command. The handler now rejects, before any `DataWriter` call or state mutation, any G41V1
request whose `count != 1` or whose value is not exactly 5 octets (`int32 LE + status`), returning
`ErrInvalidRequest` with `ParameterError` set — never a SUCCESS echo. The G12V1 path is unchanged
(`parseControlObjectHeader` still discards the count there; existing CROB suite unchanged).

Tests (`internal/outstation/g41v1_control_test.go`):
`TestOutstationG41V1F3CountValidation` — count 0 with a 5-byte value, count 2 with one value, count 2
with two records, truncated value, surplus byte; asserts rejection, `resp == nil`, and
`WriteAnalogOutput`/`WriteBinaryOutput` call counts of 0 with no state mutation.
`TestOutstationG41V1F3ValidCountOneStillExecutes` — positive control: count 1 executes once with the
byte-exact SUCCESS echo. **Revert-proof:** with the guard disabled, the count-0 and count-2 rows fail
(the old code returned a SUCCESS response, `DataLen: 14`).

### F4 — require matching echoed G41V1 setpoint value (`internal/master/master.go`)

`controlRequestKey` now also returns the request's G41V1 int32 value (four LE octets at offset 7).
`g41v1CommandStatus` requires the echoed value to equal the request value in addition to
group/variation/index; a wrong/zero value yields `CommandStatusUnknown`, which the single-shot path
turns into `ErrControlOutcomeUnknown` and quarantines the outstation — never SUCCESS. The no-blind-retry
gate and per-point status handling are unchanged.

### F5 — validate G41V1 response object structure (`internal/master/master.go`)

`parseG41V1Record` was rewritten to accept **only** exactly one G41V1 record with qualifier `0x28`,
count exactly 1, and total length exactly `header(5)+index(2)+value(4)+status(1)`, with no surplus
bytes or extra records. The legacy `0x00` response branch is no longer treated as a valid G41V1
control record. `g41v1CommandStatus` parses the object from offset 0 and rejects empty/truncated/
multi-record/surplus payloads, wrong qualifier, and group/variation/index/value mismatch — all
`CommandStatusUnknown` (fail closed). `0x17` remains unsupported. G12V1 parsing (`parseCommandStatus`,
`commandStatusForQualifier`) is untouched.

Tests (`internal/master/g41v1_response_structure_test.go`):
`TestOperateG41V1F4EchoedValueMustMatch` (wrong/zero value fail closed + quarantine; correct value
succeeds), `TestOperateG41V1F5StructureRejections` (empty/missing/count-zero/count-two/two-record/
truncated/surplus/qualifier-0x00/wrong-group/variation/index/value), `TestOperateG41V1F5ExplicitNonSuccessStatus`
(structurally valid echo with status 6 surfaces as `Blocked`). **Revert-proof:** against the pre-fix
`master.go`, F4 wrong-value and the F5 structural rows surfaced as SUCCESS.

### F6 — contradictory IIN vs G41V1 SUCCESS echo (CORRECTED 2026-11-11)

`internal/master/master.go` `resolveOperateStatus`. Question: what does G41V1 do when a
syntactically matching SUCCESS echo is accompanied by error-indicating IIN bits? At baseline
`1ebcc59` it reported `CommandStatusSuccess` and did not quarantine (confirmed by the earlier
characterization test). **Owner authorization `9d03f88`** permitted the bounded fail-closed
correction, which is now applied.

**Correction:** in `g41v1CommandStatus`, when the structurally valid echoed per-point status is
`CommandStatusSuccess`, the response IIN is reconciled **before** SUCCESS is returned, reusing the
existing `commandStatusFromIIN` mapping (no new numeric command-status values):

| IIN indication | Resulting status |
|----------------|------------------|
| `FuncUnknown`, `ObjectUnknown` | `CommandStatusNotSupported` |
| `ParameterError`, `BadConfig` | `CommandStatusBadFormat` |
| `AlreadyExecuting` | `CommandStatusAlreadyActive` |
| `LocalControl` | `CommandStatusLocal` |
| `BufferOverflow` (not positively classifiable) | `CommandStatusUnknown` → `ErrControlOutcomeUnknown` + quarantine |
| clean IIN, or non-error IIN (e.g. `Class1Events`, `NeedTime`) | `CommandStatusSuccess` |

An explicit non-SUCCESS per-point status is never overwritten with SUCCESS (surfaced as-is,
including when the IIN also carries an error). Existing control single-shot/no-blind-retry and
quarantine semantics are preserved; a positively classified failure is surfaced as that status
without an extra quarantine. G12V1's IIN-only response policy (`resolveOperateStatus` non-G41V1
branch, `commandStatusFromIIN`) is unchanged.

Tests (`internal/master/g41v1_response_structure_test.go`):
`TestOperateG41V1F6IINContradictsSuccessEcho` now asserts the desired fail-closed behavior — clear
and non-error IIN keep SUCCESS; `ParameterError`/`ObjectUnknown`/`FuncUnknown`/`BadConfig`/
`AlreadyExecuting`/`LocalControl` map to the failure statuses above; `BufferOverflow` fails closed
as UNKNOWN with `ErrControlOutcomeUnknown` and quarantine. The prior defect-characterization
assertions were removed (no passing test expects the bug).
`TestOperateG41V1F6ExplicitNonSuccessStatusPreserved` confirms an explicit non-SUCCESS status
(`Blocked`, `NoSelect`) is surfaced unchanged with clean and conflicting IIN.
**Revert-proof:** against the pre-fix `master.go`, every contradictory-IIN case surfaced SUCCESS
and `BufferOverflow` returned no error.
