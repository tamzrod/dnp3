# EVT-001 PPR-001 — bounded event batching and multi-fragment confirm

Cloud continuation checkpoint. Verified on a clean `origin/work` checkout.

## Defect

`encodeEventList` grouped one same-variation event run under a single
qualifier-`0x17` object header. `al.AppendIndexedEvents` rejects more than 255
objects in one header, so a run of 256 or more returned `nil,nil` and the whole
batch was suppressed: no events were delivered and none were removed from the
queue.

A second defect surfaced during direction-B interop. OpenDNP3 3.1.2 sets the
application CON bit on every fragment of a multi-fragment solicited response,
including the final fragment, and stays in the confirm-wait state until each is
confirmed with its own sequence. The master confirmed only the non-final
fragments and used the joined APDU's first-fragment sequence, so the peer
reported `solicited confirm with wrong seq: 1, expected: 2` and the next read
observed leftover events (SECOND delivered 30 extra at N=256).

## Correction

- `internal/outstation/event_report.go`: `encodeEventList` emits a same-variation
  run as consecutive count-bounded headers (`maxObjectsPerHeader=255`) and
  returns only the objects actually encoded. `encodeEventListBounded` bounds one
  unsolicited application fragment and leaves the remainder queued.
- `internal/outstation/outstation.go`: `MaxFragmentSize` config;
  `responseFragments`/`splitObjectData`/`indexedBlock`/`eventValueSize` split a
  solicited response larger than the peer's 2048-octet transport receive buffer
  into valid FIR/FIN application fragments. Only qualifier-`0x17` indexed runs
  are split below a header; sequential blocks stay whole.
- `internal/tl/transport.go`: transport-header bits corrected to IEEE 1815
  (FIN=0x80 bit 7, FIR=0x40 bit 6), verified against OpenDNP3 3.1.2
  `TransportHeader.cpp`.
- `internal/master/master.go`: `waitForResponseTimeout` accumulates
  multi-fragment solicited responses; `confirmPendingAppFragments` confirms every
  CON fragment with its own sequence, including the final fragment. The redundant
  confirm in `processResponse` was removed because it used the joined APDU's
  first-fragment sequence.

## Tests

- `internal/outstation/event_batch_test.go` (new): a same-variation run larger
  than 255 is split with no loss; no object is dropped or acknowledged on encode,
  framing, or transport failure.
- `internal/master/multifragment_confirm_test.go` (new): a two-fragment solicited
  response whose fragments carry CON=1 seq=1 and seq=2 is confirmed once per
  fragment with `[1 2]`.
- `internal/al/event_objects_test.go`: pins the 255-accepted / 256-rejected
  qualifier-`0x17` boundary.

## Pre-PR corrective iteration — F1 / F2 / F3 (2026-11-14)

Independent read-only pre-PR audit of `c319050ee828290022f5af61a8822fabeed74292`
issued PUSHBACK on three findings. This iteration corrects them within the
existing CURRENT `EVT-001`. The pinned OpenDNP3 3.1.2 peer was re-run in both
directions; the earlier large-batch captures are retained above and this run
adds per-N captures for 254/255/256/257/333.

### F1 — solicited event retention across a failed send

Root cause. `buildReadResponse` removed the class/direct READ event IDs with
`eventQueue.RemoveSeqs(ids)` and `cancelInFlightLocked(ids)` while the reply was
still being assembled. The `RunWithContext` send loop then ignored
`frame.Encode` and `transport.Send` failures and continued, so an accepted event
had already left the queue before its link send succeeded. A failing transport
therefore lost the event silently.

Correction. `stageSolicitedRemovalLocked` snapshots each event about to be
removed (insertion sequence, class, timestamp, flags/value) and only then removes
it; both capture sites (direct READ and class READ) call it. The send path is
`sendResponseFragments`, which returns the first encode or send error. On any
error the read loop calls `requeueSolicitedEvents`, which re-inserts every staged
event with `EventQueue.Restore` (original sequence and class buffer), then
refreshes the event IIN. A successful send leaves the staging in place and the
next request clears it. No event is dropped, no false confirmation is produced,
and a later poll re-encodes exactly the lost events. Staging happens under
`o.mu` while the queue still holds the events, so a concurrent unsolicited send
cannot remove them as well.

### F2 — oversized un-splittable response block

Root cause. `splitObjectData`/`blockSpan` keep a non-indexed block in one piece,
and `responseFragments` returned the original APDU whenever the splitter yielded
at most one chunk. A single block larger than `MaxFragmentSize` therefore
produced an oversized application fragment.

Correction. `responseFragments` now returns `([]*al.APDU, error)`. When the
object data exceeds the budget but the splitter yields a single chunk — one
un-splittable block — it returns `ErrFragmentTooLarge` instead of the original
APDU. Every emitted chunk is also length-checked against the budget. The error
propagates through `sendResponseFragments`, so the outstation fails closed
before sending and F1 re-queues the events. Valid indexed runs are still split
under fresh count-bounded headers; sequential blocks are still kept whole so no
point index is renamed.

### F3 — solicited application confirm send failure counted as done

Root cause. `confirmPendingAppFragments` ignored `sendApplicationConfirm` errors
and advanced `*done`, so `waitForResponseTimeout` could report a completed
response while the peer was still blocked in confirm-wait.

Correction. `confirmPendingAppFragments` now returns an error. A failed
confirm does not advance `done` past the unconfirmed fragment; the error is
classified through `markDisconnected` and propagated so the read fails rather
than completing. Each fragment keeps its own sequence and a successful confirm
is still sent once per fragment; the overall read deadline and bounded retry
behaviour are unchanged.

## Pre-PR corrective iteration — F4 and F2 fixture (2026-11-14)

### F4 — restore rejected when concurrent publishers refill the event buffer

Root cause. `stageSolicitedRemovalLocked` removed the accepted events from the
class buffers during READ preparation, freeing their slots. The send of a
multi-fragment response then ran in `RunWithContext` without holding the queue
mutex, so a concurrent `PublishEvent` could refill those slots. When the send
failed, `requeueSolicitedEvents` called `EventQueue.Restore`, which rejected any
event once `len(q.buffers[class]) >= maxSize/3`; the boolean was ignored, so the
originally accepted event was silently discarded in favour of the newer one.

Correction. Each staged event now holds a reservation in the queue.

- `EventQueue` gains a per-class `reserved` count. `StageSeqs` removes the
  sequences and reserves one slot per removal; `ReleaseReserved` drops a
  reservation without re-inserting (send succeeded); `Restore` consumes a
  reservation and re-inserts the event verbatim (send failed).
- `Add` and `IsFull` count `len(buffers[class]) + reserved[class]` against the
  per-class cap, so capacity held for an in-flight READ is not offered to a
  concurrent publisher. A publisher at the true limit receives the existing
  explicit `ErrEventBufferFull`, and no old or new accepted event is dropped.
- `Restore` reports false only when no reservation is held, and
  `requeueSolicitedEvents` now checks the result, increments a `restoreFailures`
  counter, and (only under `DNP3_DEBUG=1`) logs a diagnostic. A non-zero counter
  is a correctness alarm, not a silent drop.
- `releaseSolicitedEvents` releases the reservations once the whole response is
  delivered, so delivered slots become reusable. `discardSolicitedLocked`
  releases reservations from a staging that was never sent (a direct
  `ProcessRequest` caller), preventing a leak.

Delivery indeterminacy. A partly transmitted multi-fragment response may already
have reached the peer, so restored events can be delivered at least once on the
next poll. There is no blind replay loop; the reservation bounds memory to the
per-class cap. Transport `Send` success is not treated as peer receipt.

### F2 fixture — test a valid oversized static block

The prior fixture used 300 packed G1V1 binary points under qualifier `0x07` with
count byte `0x2C` (=44), which is not a valid encoding of 300 objects. The
fixture now uses 255 packed G1V1 points: qualifier `0x07`, count byte `0xFF`
(=255, the largest an 8-bit count can express), 32 packed data octets
(alternating `0x55`), a 36-octet block, versus a 32-octet application-fragment
budget. `TestOversizeFixtureIsWireValid` asserts the header count, packed length,
bit mapping and that the public `buildBinaryInputData` emits exactly those bytes
and that they exceed the budget. `TestSolicitedOversizeBlockFailsClosed` and
`TestResponseFragmentsOversizeBlockErrors` now use this block and still fail
closed. Malformed/truncated and unknown-block fail-closed tests are retained
separately and are not described as valid oversized input.

## PPR-001-S1/S2 — public-profile gate and 0x15 alias (2026-11-14)

Cloud continuation checkpoint on the same clean `origin/work` lineage.

### S2 — misleading `FuncGetIdentifier = 21` alias

`internal/al/function_codes.go` carried a legacy constant
`FuncGetIdentifier = 21` (decimal) that aliased the canonical
`FuncDisableUnsolicited = 0x15` (also 21). The only references were the constant
itself and a `code == FuncGetIdentifier ||` term in the `CategoryConfiguration`
predicate. There were no external callers. Correction:

- Removed `FuncGetIdentifier` and its `CategoryConfiguration` term. The canonical
  constants `FuncEnableUnsolicited = 0x14` (20) and `FuncDisableUnsolicited = 0x15`
  (21) are retained and remain the sole unsolicited mapping; no wire behavior
  changed.
- New `internal/al/function_codes_test.go` pins the canonical mapping: 0x14 is
  enable, 0x15 is disable, both are configuration functions, and the former
  decimal 21 name no longer resolves to a separate identifier.

### S1 — public unsolicited/event surface vs the published profile

`active_work/supported-profile.md` makes unsolicited/event delivery a v0
**Reject** option, but PR #29 exposed operational public entry points
(master `EnableUnsolicited`/`DisableUnsolicited`/`ReadEvents`/`WatchUnsolicited`/
`SetUnsolicitedHandler`, outstation publishing/`SetUnsolicitedHandler`/
`WithUnsolicitedMode`). The published profile is unchanged. The public surface is
now Reject by default, behind one explicit, non-default switch per side:

- Master: new `Config.ExperimentalEventDelivery` and
  `WithExperimentalEventDelivery()`. Without it, the five public methods return
  `ErrUnsupportedOption` before any wire traffic and `SetUnsolicitedHandler`
  registers no handler; the internal unsolicited callback is not installed.
- Outstation: new `Config.ExperimentalEventDelivery` and
  `WithExperimentalEventDelivery()`. Without it, `PublishBinaryEvent`/
  `PublishAnalogEvent`/`PublishCounterEvent` return `ErrUnsupportedOption`,
  `SetUnsolicitedHandler` registers no handler, and `WithUnsolicitedMode(true)`
  is rejected by `NewServer` (`ConfigurationError` on `UnsolicitedMode`).
- With the switch set, the existing EVT-001 internal/isolated behavior is
  unchanged: enable/disable reach the wire as 0x14/0x15, events publish and
  deliver, and the `lab/evt001` harness opts in explicitly.

This is a gating change only. No wire semantics, Class-0 read, CROB, or G41
behavior changed, and the published supported profile is neither edited nor
promoted.

### RED-before / GREEN-after

On a copy with only the S1 gates and the S2 alias removal reverted (pre-fix
source, new tests kept), `TestUnsolicitedRejectedByDefault`,
`TestUnsolicitedRejectedWhileConnected`, `TestOutstationEventsRejectedByDefault`

enable / 0x15 disable) that must never change, so it is a guard rather than a
behavioral flip; the misleading alias is instead removed outright, so any caller
of `FuncGetIdentifier` now fails to compile.
