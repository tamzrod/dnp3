  `cpp/lib/src/outstation/CommandResponseHandler.cpp`, `cpp/lib/include/opendnp3/gen/CommandStatus.h`.

### 3.1 G41 variation → type (authoritative)

| Variation | Type | Object size | Layout (serialized) |
|---|---|---|---|
| **G41V1** | 32-bit signed integer (`int32_t`) | 5 | `value(4, LE)`, `status(1)` |
| **G41V2** | 16-bit signed integer (`int16_t`) | 3 | `value(2, LE)`, `status(1)` |
| **G41V3** | single-precision float (`float`) | 5 | `value(4, LE)`, `status(1)` |
| **G41V4** | double-precision float (`double`) | 9 | `value(8, LE)`, `status(1)` |

`Group41VarN::Write` is literally `LittleEndian::write(buffer, arg.value, arg.status)` for all four
variations → **value little-endian, then one status octet**. `Group41Var0` (any) has no serializer.
`AnalogOutput<T>` documents the mapping explicitly (Int16→V2, Int32→V1, Float32→V3, Double64→V4).

### 3.2 Request object header and qualifier (authoritative)

- `CommandSetOps::IsAllowed` accepts **only** qualifiers `UINT8_CNT_UINT8_INDEX` (0x17) and
  `UINT16_CNT_UINT16_INDEX` (0x28) for G12V1 and G41V1–V4 control requests.
- `TypedCommandHeader::Write` emits `count` then, per record, an **index prefix** (1 or 2 octets)
  followed by the object → `header(group,var,qual) ‖ count ‖ [index ‖ value ‖ status] …`.
- The request object's `status` field is `CommandStatus::SUCCESS` (0) by default.

### 3.3 Response contract (authoritative)

- `CommandResponseHandler` responds using the **same** `Group41VarN` serializer
  (`RespondToHeader<AnalogOutputInt32, …>(…, Group41Var1::Inst(), …)` etc.) → the response **echoes
  the object (value + status octet)** under the matching qualifier, with the status octet replaced by
  the command result. G41 command responses are therefore **object-with-status**, not status-only.
- `CommandStatus` (peer): `SUCCESS=0, TIMEOUT=1, NO_SELECT=2, FORMAT_ERROR=3, NOT_SUPPORTED=4,
  ALREADY_ACTIVE=5, HARDWARE_ERROR=6, LOCAL=7, TOO_MANY_OPS=8, NOT_AUTHORIZED=9, …,
  DOWNSTREAM_LOCAL=13`. This matches the repo's `types.ControlStatus` for 0–9.

## 5. Proposed implementation contract (Direct-Operate-first) — for AO-002+

Contract only; **no implementation in AO-001**.

### 5.1 Scope

- **Operation mode:** Direct-Operate **with response** only. SBO and Direct-Operate-No-Response stay
  `Reject` until a separate human-approved profile (roadmap constraint).
- **Variations:** G41V1 (int32), G41V2 (int16), G41V3 (float32), G41V4 (float64), each explicitly
  gated. Any variation not in the verified set is **rejected**, never silently coerced.
- **Qualifier:** emit `0x28` (UINT16_CNT_UINT16_INDEX) as the primary; accept `0x17` on receive;
  reject all others for control objects.

### 5.2 Wire contract (must be byte-exact)

- Master request: `group=41, variation∈{1,2,3,4}, qualifier=0x28, count=1 ‖ index(2, LE) ‖ value(LE) ‖ status(0x00)`.
- Outstation response: same object echoed, `status` = command result, under `0x28` (or `0x17` if received).
- All multi-octet fields **little-endian** (DNP3 LSB-first); index is 2-octet LE.

### 5.3 Value handling (never silently convert)

- **Integer variations (V1/V2):** require an exactly-representable integer source; reject float sources
  that are non-integral or out of range for the target width (no truncation). Out-of-range → reject,
  not wrap.
- **Float variations (V3/V4):** accept IEEE-754; define explicit policy for `NaN`/`±Inf`
  (recommend **reject** at the API boundary rather than transmit) and document it.
- **Cross-type mismatch** (e.g. int source to float variation) is rejected unless an explicit,
  documented, lossless conversion is chosen. `AnalogCommandValue` (single `float64`) exactly represents all int32 values, but cannot
  faithfully represent all int64 values above 2^53 — the API boundary should expose typed values
  for each variation and enforce exact, in-range conversions.

### 5.4 Failure / safety contract (must hold)

- Unknown variation, wrong length, truncated prefix, bad qualifier, or index out of the point map →
  **reject with no side effect**; set `IIN.PARAMETER_ERROR` on the outstation; never partial-apply.
- A command is **not** successful on transport acceptance alone: require a parsed per-point
  `CommandStatus == SUCCESS` from the response object (fix D4); anything else is a failure.
- Timeout / disconnect / ambiguous outcome → **no blind retry**; reuse the existing single-shot
  control gate and quarantine semantics (`AcquireControlGate`, `QuarantineOutstation`).
- Concurrency: one non-idempotent control per outstation at a time (existing gate); reject-with-no-
  side-effect on a rejected command; never reorder or coalesce.
- Reject-with-no-side-effect must be proven: a rejected command must not call the handler nor change
  outstation state.

### 5.5 Required API-boundary changes (AO-002 decision, not done here)

- Replace the single `AnalogCommandValue{float64}` with a **typed** analog command value (or per-
  variation constructors) so int32/int64/float32/float64 setpoints round-trip exactly.
- Add an explicit **group/variation allow-list gate** on the control path (fix D3) that fails closed.
- Make the master control-status parser **group-aware** (fix D4) covering G12V1 and the enabled
  G41 variations.
- Review the outstation bridge `CommandType` (fix D6) and ensure the outstation emits a real
  per-point command-status object for control responses.
- Any such public-API change needs its own approval note (public API stability, `AGENTS.md`).

### 6.1 Independent golden vectors (NOT generated by code-under-test)

Derived independently from §3 (spec/peer) in this session; to be frozen as literal bytes in tests:

| Case | Object bytes (hex, incl. status) |
|---|---|
| G41V1 int32 = 2300 | `FC 08 00 00 00` |
| G41V1 int32 = −1 | `FF FF FF FF 00` |
| G41V2 int16 = 42 | `2A 00 00` |
| G41V2 int16 = −32768 | `00 80 00` |
| G41V3 float32 = 2300.0 | `00 C0 0F 45 00` |
| G41V3 float32 = −0.5 | `00 00 00 BF 00` |
| G41V4 float64 = 123.456789 | `0B 0B EE 07 3C DD 5E 40 00` |
| G41V3 float32 = NaN | `00 00 C0 7F 00` (policy case) |
| G41V3 float32 = +Inf | `00 00 80 7F 00` (policy case) |

Full object-header-and-record golden: `group(0x29) variation(0x01–0x04) qualifier(0x28) count(01 00) ‖ index LE(2 bytes) ‖ value LE ‖ status(00)` for both
master-encode and outstation-decode. `0x28` is the qualifier, **not** the variation; `0x29` is Group 41.

### 6.2 Negative / adversarial vectors

- Unknown variation (e.g. V5), qualifier `0x00`/other, truncated value, count mismatch, index beyond
  the point map → reject + `IIN.PARAMETER_ERROR`, **no** handler call, **no** state change.
- `NaN`/`±Inf` per chosen policy; int out-of-range / non-integral float for integer variations.
- Response with non-SUCCESS status → surface as failure (not success); response missing the object →
  `Unknown` (no assumed success).

### 6.3 In-repo tests (AO-002)

- Byte-exact encoder goldens (master `buildControlRequest`, outstation `executeControl`) for each
  enabled variation, asserted against §6.1 literals.
- Round-trip master↔outstation over real TCP (loopback) for the enabled subset — **necessary but not
  sufficient** (D2 shows a self-consistent BE bug would pass it).

### 6.4 Future isolated independent peer verification (AO-004)

- Isolated `network_mode: none` container, two namespaces, one veth — as in the VEC-01 lab.
- **Memory-only** simulated setpoint handler (no physical I/O, no live grid).
- Positive + negative capture, independent decode (tshark), original PCAP + packet-derived `.vec`,
  `SHA256SUMS.txt`, scoped evidence statement. Do **not** equate this with general conformance.

   Direct-Operate vs SBO policy, select/operate timing, and response expectations are **not provided**.
   These must not be invented or hardwired (roadmap constraint). Project-specific integration is

   actual peer vectors, not guesses. G41V1–V4 are spec-defined; prioritisation is a product decision.

   `float64`, but int64 values above 2^53 may lose integer precision. G41V1 uses int32;
   a typed per-variation API and strict range/integrality checks remain a design decision.
4. **KDE/design approval:** public-API and supported-profile changes (and any control-safety policy
   change) require the normal approval path; AO-001 grants none.
5. **G1V2 mis-decode** (from VEC-01) is unrelated and remains unsupported/known-broken; not in this
   mission.
