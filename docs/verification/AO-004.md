### H.4 Triangulation (distinguishing the four candidate causes)

**(a) OpenDNP3 signed-zero / subnormal normalization — CONFIRMED as the wire-visible divergence.** The
independent pinned peer, on decode of a G41 float, echoes the value through ser4cpp's
`SingleFloat`/`DoubleFloat` codec, which is **not** a raw-bit copy:

- `ser4cpp::SingleFloat::to_float32` special-cases `exponent==0 && mantissa==0` → returns literal `0.0f`
  **before** the sign is applied, so **both `+0.0` and `-0.0` decode to `+0.0`** (the sign bit is lost).
- `to_float32` for subnormals computes `std::ldexp(weighted_mantissa, -126)` and then a separate
  `if(sign) result=-result`; `to_uint32` re-encodes with `std::frexp` and `(uint32_t)(fraction_part *
  (1<<24)) & 0x7FFFFF`. Re-encoding a subnormal (e.g. `0x00000001`) yields **`0x00000000`**.
- `ser4cpp::DoubleFloat` has the identical `exponent==0 && mantissa==0 → 0.0` and `frexp`-based
  `to_uint64` structure, so the G41V4 negative-zero and smallest-subnormal echoes are likewise `+0.0`.

This was **reproduced offline** against a faithful copy of the pinned codec compiled with the peer's
release flags (`-O3 -DNDEBUG`): inputs `0x80000000`, `0x00000001`, `0x00000002`, `0x007FFFFF` all decode
to `0x00000000` (`LOSSY`), while `1.5` (`0x3FC00000`), `-1.0` (`0xBF800000`) and max-finite
(`0x7F7FFFFF`) round-trip `MATCH`. The peer's G41 command handler is memory-only and does no arithmetic
on the value; the loss is entirely in the ser4cpp float (de)serialization used to parse and re-echo the
object.

**(b) Go parser strict echo-bit check / response correlation — correct, not a bug.** `controlRequestKey`
recovered the request as `G41/V3/index 0` with value `0x80000000`; `parseG41Record` parsed the response as
exactly one `G41/V3` record, qualifier `0x28`, count 1, index 0, value `0x00000000`, status `0`; the
value comparison failed, so `g41CommandStatus` returned `CommandStatusUnknown`. The Go strict raw-bit
comparison is intentional and **must not be cleared/bypassed**; it correctly refused to treat a
sign-flipped echo as success. The prior run's in-repo G41V3 tests pass because the in-repo outstation
echoes exact bits, whereas the independent peer does not.

**(c) Response lost / truncated / wrong sequence — RULED OUT.** Every request has a matching response with
the correct transport sequence and application sequence (`AC`), correct `dest/src` addresses, and valid

### H.5 Root cause (evidence-backed)

### I.2 Invalid-index cases (Appendix H run-2 indices 22–25) — packet evidence (secondhand)

From Appendix H §H.6, the four invalid-index cases are G41V1/V2/V3/V4 with **request `index = 1`**,

Key point (packet-level, secondhand): the response **was delivered and correlated** (not lost, not

### I.3 Root cause (firsthand, Go source) — `0x0C`/12 has no mapped status → `ControlTimeout`

Trace (all read-only, `8ab00ef`):

1. **Internal enum omits 11/12.** `internal/master/master.go` `type CommandStatus uint8` defines only
   `0…10` and `0xFF` (`CommandStatusUnknown`). There is **no** constant for `11` or `12`; in particular
   **no `OUT_OF_RANGE` value**. (Grep for out-of-range/`= 12`/`CommandStatus(12)` finds nothing.)
2. **Per-point status is read verbatim.** `parseG41Record` returns `status = CommandStatus(data[offset+7+
   width])`, and `g41CommandStatus` returns that status **as-is** when the echoed variation/index/value
   match the request (Appendix H §H.4(b): index 1 echoes bit-identically, so the match succeeds and the
   status is **not** downgraded to `Unknown`). Thus for `0x0C` it returns `CommandStatus(0x0C) ==
   CommandStatus(12)` — a value with **no defined constant**.
3. **`sendControlOnce` treats any non-`Unknown` value as a classified outcome.** `if status ==
   CommandStatusUnknown { … ErrControlOutcomeUnknown }` else it returns `(status, nil)`. Since `12 !=
   0xFF`, it returns `status = 12` with **`err == nil`** and logs `control outcome 12`; the outstation is
   **not** quarantined (the command outcome is definite: remote rejection).
4. **Public mapping has no case for 12 → default → `ControlTimeout`.** `pkg/dnp3/master/client.go`
   `mapCommandStatus` switches on the defined constants and has a `default` that returns
   **`types.ControlTimeout`**. `CommandStatus(12)` matches **no** case (its 12 is not
   `CommandStatusAutonomous`=10, and the internal enum has no 11/12), so it falls to `default` →
   **`types.ControlTimeout`**. `client.Operate` then returns `&OperateResponse{Status:
   mapCommandStatus(cs)}` with **`err == nil`**.

**Conclusion:** For invalid-index G41 controls the remote definitively rejects the point with `0x0C`
(OUT_OF_RANGE), the Go master correctly parses and does **not** quarantine (the outcome is known), but the
**public status mapping has no representation for code 12**, so the `default` branch mislabels a
**definite remote rejection as `ControlTimeout`** (and, incidentally, the same `default` collapses
`CommandStatusUnknown`/quarantine-ambiguity and any unknown code into the same `ControlTimeout`).

**Confidence:** **HIGH** for the Go source chain (steps 1–4 are direct code facts). **MEDIUM–HIGH** for the
end-to-end explanation, because the wire premise (response carried `0x0C` with `err == nil` at the
internal layer) is **secondhand** from Appendix H (`RAW_PCAP_UNAVAILABLE` to re-verify here). The
alternative that the API timed out **without** receiving a response is **not supported** by Appendix H
(which records complete, CRC-valid, correctly-sequenced responses for indices 22–25) and is inconsistent
with `sendControlOnce`'s response-missing path (that path returns `ErrControlOutcomeUnknown`, not a bare
`ControlTimeout`). Labelled **hypothesis** pending raw re-verification: the harness reported only the
`OperateResponse.Status` value (`ControlTimeout`) and did not also surface the `err == nil` / internal
status `12`, which is why the mislabel was not obvious at the API boundary.
