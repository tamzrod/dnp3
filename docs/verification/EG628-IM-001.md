## 3. Independent reproduction method

Generic in-memory outstation (`NewOutstation` + a `DataHandler`), no EG628 code,
no hardware, no tester-specific branching.

- Class 0+1+2+3 request emitted as `G60V1..V4 / qualifier 0x06`.
- Responses decoded by a **separate minimal Python decoder** (`/tmp/indep_decode.py`)
  written from IEEE 1815 object-header and object-layout rules, deriving the
  prefix width from the qualifier and not reusing the Go reader.
- Sweep of 2 665 configurations (BI 0–40, AI 0–12, CTR 0–4 × BO/AO 2) decoded
  **clean** — no malformed header at any small point count. This is the negative
  control that rules out a small-configuration encoding bug.

Default 5-point responses (G1V1, G30V1, G20V1, G10V1, G40V1) decode correctly,
including the flags-first field order already pinned by
`internal/outstation/field_order_test.go`.

## 4. Defect A — request-scoped IIN error bits persisted across requests

**Location:** `internal/outstation/outstation.go`, `ProcessRequest`.

`o.iin.ParameterError` (and `ObjectUnknown`) were set when a request was rejected
and were only cleared by `o.iin = al.IIN{}` on a restart path. IEEE 1815 IIN
describes the response that carries it, so every later reply inherited the error.

**Reproduced:** a rejected G41 WRITE, then a valid Class-0 READ, returned
`iin=0004` (`ParameterError`) on the READ that contained no parameter error.

This is a plausible contributor to the reported `IIN PARAMETER_ERROR` on a READ,
but the causal link to the EG628 session is **not proven** without the capture.

**Fix:** clear `FuncUnknown`, `ObjectUnknown`, `ParameterError` at the top of
`ProcessRequest`, before dispatch. Station conditions (event availability, buffer
overflow, device trouble, need-time) are untouched and still reported.

## 5. Defect B — 8-bit count qualifier truncated above 255 points

**Location:** static builders `buildBinaryInputData`, `buildAnalogInputData`,
`buildCounterData`, `buildBinaryOutputData`, `buildAnalogOutputData`.

Each wrote the point count as `byte(len(data))`. Above 255 points this wraps:
300 binary inputs produced header `1,1,0x07,0x2C` (count 44) followed by 38 packed
octets. A strict peer parser then reads a packed octet as the next object header
and desynchronises — the same *class* of failure as "truncated object data".
The indexed branch (`0x17`) additionally cannot address index 256+ because its
prefix is one octet.

The event path already guarded this (`maxObjectsPerHeader`); the static path did not.

**Reproduced:** 300-BI configuration → independent decoder reported
`unsupported qualifier 0x55 at offset 10`; sweep over 250–340 BI showed failure for
every count ≥ 256 and clean decode at ≤ 255.

**Fix:** two helpers in `outstation.go`:

- `appendSequentialCount` — `0x07` + 8-bit count at ≤ 255, else `0x27` + 16-bit count.
- `appendIndexedCount` — `0x17` + 8-bit count at ≤ 255, else fall back to a
  sequential `0x27` block and omit the per-point index prefix.

Counts at or below 255 emit exactly the same bytes as before, so the existing
pinned goldens are unchanged.

**Relation to the report:** this requires more than 255 points in one group. The
reported capture does not exist, so it is **not** established that the EG628
configuration exceeded 255 points or that this defect produced offset 38.
